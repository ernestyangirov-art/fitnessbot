# fitnessbot — контекст проекта

Телеграм-бот персонального тренинга и питания для одного пользователя (Эрнест).
Хостинг: Render.com, бесплатный тариф (важно — см. ниже). Google Sheets как база
данных. Два репозитория:

- **fitnessbot** (этот) — сам бот
- **gymup-sync** (отдельный, приватный) — синхронизация GymUp → Sheets,
  запускается через GitHub Actions по расписанию

## Правила работы со мной

- Никакой «воды», приветственных дифирамбов, пустых рассуждений.
- Двигаемся короткими, итеративными шагами. Не выдавать неконтролируемые
  полотна кода без согласования.
- Перед внедрением крупной фичи: сначала кратко опиши логику/математику и
  задай уточняющие вопросы, если есть развилки в решении.
- Код только в 100% рабочем виде: асинхронность (`asyncio.to_thread` для
  блокирующих вызовов Google API), защита от падений (`try/except` там, где
  внешние вызовы), без непроверенных предположений о структуре данных —
  проверяй на реальных данных из таблицы, если есть возможность.
- Прямая обратная связь без лести. Если решение спорное — говори об этом до
  реализации, а не после.

## Критическое ограничение инфраструктуры

**Render бесплатный тариф засыпает после ~15 минут без входящего HTTP-трафика.**
Это определяет архитектуру:

- Внутренний планировщик (APScheduler) **не используется** — сознательно убран.
  Спящий процесс не может сработать по таймеру.
- Все запланированные действия (пуши, синхронизация) идут **снаружи**, через
  GitHub Actions по cron, которые бьют по HTTP-эндпоинтам бота. Запрос будит
  сервис (до ~50–60 сек на холodный старт) и одновременно триггерит действие.
- Настройки пользователя, история и всё персистентное состояние живёт в Google
  Sheets, а не на диске Render — диск эфемерный, стирается при каждом
  рестарте/деплое.

Если предлагаешь новую периодическую функцию — она обязана идти через
GitHub Actions + HTTP-эндпоинт `/cron/<name>`, а не через APScheduler.

**Keep-alive (с 17.08.2026):** `.github/workflows/keepalive.yml` бьёт по
`/healthz` каждые 5 минут, чтобы сервис не засыпал вообще — тогда пуши
и обычные ответы бота идут без холодного старта. Проверено по биллингу
Render: 750 бесплатных instance-hours/месяц, на аккаунте всего 1 сервис —
круглосуточная работа съедает ~744ч/мес, укладывается с запасом. Если
появится второй бесплатный сервис на аккаунте — лимит нужно пересчитать,
750ч делятся на все сервисы разом. Это не отменяет архитектуру выше:
`/cron/*` всё ещё нужен для доставки самих пушей, keep-alive только
убирает задержку холодного старта.

## Структура репозитория

```
core.py       — конфиг, доступ к Google Sheets, клиент Gemini, утилиты (num, cut, bar, progress_bar), настройки пользователя
analytics.py  — аналитика тренировок: build_analytics (шкалы), collect_facts + get_analysis (разбор от модели, кэшируется)
food.py       — дневник еды: запись, редактирование, избранное, форматирование
weight.py     — вес тела: запись, история, weight_for_date (вес на конкретную дату для исторических расчётов)
bot.py        — телеграм-хендлеры, клавиатуры, запуск, HTTP-эндпоинты для cron
requirements.txt
```

Модули не знают про aiogram/Telegram — это забота `bot.py`. `core.py`,
`analytics.py`, `food.py`, `weight.py` можно тестировать без поднятия бота.

Функции переименованы без подчёркивания (`num`, не `_num`) там, где
используются из других модулей — подчёркивание означает «приватное».

```
BODYWEIGHT_KG      — используется в sync_gymup.py (репозиторий gymup-sync), не здесь
```

## GitHub Actions secrets (репозиторий fitnessbot)

```
BOT_URL            — https://fitnessbot-i18u.onrender.com, читает keepalive.yml
```
Это отдельный набор от переменных окружения Render выше — секреты GitHub
Actions живут в самом репозитории (Settings → Secrets → Actions), не в
Render. `secrets.BOT_URL` в gymup-sync — свой, независимый секрет с тем
же значением, задан там же по той же причине (нельзя шарить секреты
между репозиториями напрямую).

`SPREADSHEET_ID` и прочие ID НЕ хардкодить дефолтами в коде — раньше были
захардкожены, убрано по соображениям гигиены (репозиторий публичный). Если
переменная не задана — падать с понятной ошибкой, а не работать «как получится».

## Резолв колонок по заголовку (с 17.08.2026)

Индексы колонок (`COL_*` в analytics.py, `M_*`/`F_*` в food.py, `S_*`/`A_*`
в core.py/analytics.py) больше **не хардкодятся числами** — резолвятся из
первой строки листа через `core.header_index(header_row, required, sheet_name)`
при каждом `food_sheet()`/`settings_sheet()`/`read_training_rows()` и т.п.
Если ожидаемой колонки нет — `RuntimeError` с понятным текстом, а не тихое
чтение не той ячейки. Сами названия констант не поменялись, поменялся только
момент, когда они получают значение (см. `global` в `_resolve_*_columns()`
каждого модуля) — везде, где эти константы использовались раньше, код не
трогали.

Два разных режима в `open_sheet(title, headers=…)`:
- **headers передан** (Настройки, Питание, Избранное, Разбор) — лист целиком
  свой, бот вправе дописывать в конец строки заголовков колонки, которых там
  не хватает по сравнению с объявленной схемой в коде. Это чинит рассинхрон
  «в коде завели новую колонку, а в реальном листе её нет» само, без ручной
  правки таблицы. Так и обнаружился реальный баг: `weight_notify` был добавлен
  в код, но не в саму таблицу «Настройки» — тоггл писал TRUE/FALSE в колонку
  без заголовка.
- **headers не передан** (Тренировки — пишет sync_gymup.py) — лист чужой,
  бот его не создаёт и не правит, только строго требует нужные колонки.

## Схемы листов Google Sheets

### «Тренировки» (пишет sync_gymup.py из gymup-sync, читает analytics.py)
16 колонок, индексы резолвятся по заголовку (см. выше), не хардкодятся:

```
0  set_id                        — ключ дедупликации, стабильный ID подхода из GymUp
1  Дата и время
2  Программа                     — program.name из GymUp (НЕ training.name — оно всегда NULL)
3  Сплит                         — day.name из GymUp
4  Упражнение                    — из словаря exercise_names.py (в GymUp пусто везде)
5  ex_id                         — стабильный id упражнения GymUp, ключ для EXERCISE_PATTERNS
6  Подход №
7  Вес (кг)
8  Повторы
9  Тоннаж внешний (кг)           — вес*повторы, БЕЗ собственного веса
10 Тоннаж с весом тела (кг)      — для упражнений с весом=0 (подтягивания и т.п.)
11 Расчётный 1ПМ (кг)            — пусто, если вес=0 (1ПМ от нулевого веса бессмыслен)
12 Тяжесть (1-5)                 — hard_sense из GymUp, критерий "тяжёлого подхода" — >=4
13 Интервал до след. подхода (с) — из finishDateTime, НЕ то же самое что плановый restTime
14 Суперсет                      — метка связки (parent_id в GymUp), например "С1"
15 Комментарий
```

Дедупликация синхронизации — по колонке 0 (`set_id`), сравнение чисел.
НЕ склеивать строки в ключ — старая версия так делала и давала 5x дубли.

### «Разбор» (analytics.py, кэш LLM-разбора)
```
Ключ сессии | Разбор | Сгенерирован
```
Ключ = дата-время последней сессии (`last_key` из group_sessions). Разбор
считается **один раз на сессию** и кэшируется — новых тренировок не бывает
без новой синхронизации, поэтому пересчитывать при каждом нажатии кнопки
бессмысленно и дорого. Чтобы форсировать пересчёт — удалить строку вручную.

### «Питание» (food.py)
```
meal_id | Дата и время | Блюдо | Вес порции (г) | Ингредиенты |
Белки (г) | Жиры (г) | Углеводы (г) | Клетчатка (г) | Калории | Источник |
Ручные поля
```
`Ингредиенты` — сырьё для будущего пересчёта микронутриентов через USDA
FoodData Central (этап Б, ещё не сделан). Модель определяет состав и
граммовки, справочник считает нутриенты — модель НЕ должна выдумывать
витамины/минералы, у неё нет для этого данных.

`Ручные поля` — comma-separated список ключей (`dish`/`protein`/`fat`/
`carbs`/`fiber`/`calories`), которые правили руками через `edit_meal_field()`
(кнопка «✏️ Правка БЖУ» на карточке приёма пищи). `rescale_meal(meal_id,
new_weight)` пересчитывает БЖУ+калории пропорционально по весу порции, но
пропускает поля из этого списка — иначе кнопки +50г/−50г затирали бы ручной
ввод. Вес порции через этот механизм не редактируется — у него свой поток
(−50/+50/✏️ Вес → `rescale_meal`), он двигает пересчёт, а не является его
целью.

### «Избранное» (food.py)
```
fav_id | Блюдо | Вес порции (г) | Ингредиенты |
Белки (г) | Жиры (г) | Углеводы (г) | Клетчатка (г) | Калории | Использований
```
Повтор по названию блюда не создаёт дубль — возвращает существующий fav_id.
Автодобавление после `FAV_AUTO_AFTER = 3` повторов одного блюда.

### «Настройки» (core.py)
```
chat_id | morning_notify | casein_notify | weight_notify |
daily_protein_target | daily_calorie_target
```
Кэшируется в памяти процесса (`_settings_cache`), обновляется с `force=True`
перед рассылкой пушей — иначе изменения настроек не подхватятся до рестарта.

`daily_protein_target`/`daily_calorie_target` — персональные цели по БЖУ,
правятся через `/settings` → «🥩 Цель по белку»/«🔥 Цель по калориям» → FSM.
`core.DAILY_PROTEIN_TARGET`/`DAILY_CALORIE_TARGET` остались как дефолты для
пользователя без своей записи — не удалять, на них ссылается `DEFAULT_CONFIG`
и `food._targets()`. Валидация диапазоном (`PROTEIN_TARGET_RANGE`,
`CALORIE_TARGET_RANGE` в core.py) — та же защита от опечаток, что у веса тела.

### «Вес» (weight.py)
```
Дата | Вес (кг)
```
Одна запись на дату — повторный ввод в тот же день перезаписывает строку,
не плодит дубли. Валидация диапазоном 30–300 кг (защита от опечаток вроде
8.5 или 850). `weight_for_date(day)` — вес, ближайший по времени к указанной
дате; используется там, где нужен исторически корректный вес тела (а не
последний известный), иначе старые тренировки с подтягиваниями пересчитаются
по сегодняшнему весу.

## Принятые архитектурные решения (не переоткрывать без причины)

1. **Синхронизация GymUp живёт только в gymup-sync**, бот её не делает и не
   должен. Раньше был дублирующий механизм внутри бота — убран, он плодил
   дубли вместе с внешним cron.

2. **google-generativeai (legacy SDK) заменён на google-genai.** Модель по
   умолчанию `gemini-3.6-flash` (переопределяется `GEMINI_MODEL`).
   `gemini-1.5-flash` мертва (404), не использовать.

3. **Названия упражнений — статический словарь `exercise_names.py`**
   (в gymup-sync), не эвристика по ключевым словам. В самой базе GymUp
   `th_exercise.name` пусто во всех записях — сопоставление id→название
   сделано вручную один раз по скриншотам приложения, восстановить
   автоматически невозможно.

4. **Паттерны движения (EXERCISE_PATTERNS в analytics.py)** — по id
   упражнения, выведены из кодов мышц GymUp + ручные правки, НЕ
   keyword-поиском по названию («тяга»/«жим» и т.п. — ненадёжно, разные
   упражнения могут содержать одинаковые слова).

5. **Тяжёлый подход = `hard_sense >= 4`** (шкала 1-5 из GymUp, ставится
   постфактум пользователем). Не путать с RIR — это другая метрика, в
   данных RIR нет вообще, только субъективная тяжесть.

6. **Разбор от LLM (analytics.py) — жёсткий промпт с запретами:**
   - только приведённые числа, ничего не выдумывать
   - не объяснять причины, которых нет в данных (утомление, восстановление,
     сон — этого нет в датасете, модель такое придумывает по умолчанию)
   - критика только по тренду из 3+ сессий, разовое отклонение — просто
     констатировать
   - рекомендации только в терминах конкретного упражнения (вес×повторы),
     НЕ в терминах производных величин (средний вес на подход, средняя
     тяжесть) — ими нельзя управлять напрямую, они складываются из состава
     тренировки
   - скачок 1ПМ обычно = смена снаряда/диапазона повторов, не прирост силы
   - первый подход с заметно меньшим весом = разминка, не разминка. Это
     регулярно ловилось моделью неверно до явного правила.
   Если промпт меняется — сохранять эти правила, они появились не просто так,
   каждое — реакция на конкретную ошибку модели в предыдущих версиях.

7. **Питание: модель определяет состав и граммовки, справочник считает
   нутриенты** (этап Б, не реализован). НЕ просить модель оценивать
   витамины/минералы по фото — она их не может знать, будет выдумывать
   правдоподобные числа. Это критично, если/когда будет блок БАДов —
   решения о дозировках на основе выдуманных цифр опасны.

8. **HTML-разметка вместо Markdown** в сообщениях бота — Markdown ломается
   на названиях с подчёркиваниями и не даёт нормально выровнять
   псевдографические шкалы (`<pre>` блоки).

9. **Дедупликация везде по стабильному ID, не по склейке полей строки.**
   Уроки из старой версии: сравнение через `str(list) == str(tuple)` никогда
   не совпадает, `str(None)` != пустая строка и т.п. — если где-то появляется
   похожая дедупликация, делать по id.

10. **Колонки листов резолвятся по заголовку, не хардкодятся индексом**
    (см. «Резолв колонок по заголовку» выше). Листы, которыми бот владеет,
    можно дополнять новыми колонками в коде без ручной правки таблицы —
    `open_sheet()` дописывает недостающие сам. Лист «Тренировки» — чужой
    (gymup-sync), для него только строгая проверка, никакого авто-дописывания.

## Известные ограничения / зоны риска

- `BODYWEIGHT_KG` в sync_gymup.py — env-переменная с дефолтом 85.0, статична.
  После внедрения weight.py стоит рассмотреть подстановку исторического веса
  через `weight_for_date()` вместо константы (пока не сделано).
- Telegram режет сообщение на 4096 символов — аналитика и разбор шлются
  отдельными сообщениями по этой причине, не объединять в одно без проверки
  длины.
- `find_meal`/`find_meal` в food.py читают весь лист построчно в цикле —
  нормально при текущих объёмах, но если записей станет много (тысячи),
  стоит подумать об индексации или ограничении окна поиска.
